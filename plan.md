## 5. Блок 3: 4 задачи (делай последовательно)

### 🔹 Задача 3.1 — SQL: справочники уровней и навыков мастеров

**Цель:** добавить в БД два справочника:

1. `master_levels` — уровни мастеров (4 фиксированных уровня)
2. `master_skills` — навыки/сложные работы, которые может выполнять мастер

Если аналогичные таблицы уже есть — **не дублируем**, а **аккуратно дополняем**.

**Пример базовой структуры (ориентир, можно немного корректировать, учитывая текущую схему):**

```sql
master_levels (
  id smallint primary key,         -- 1..4
  name text not null,              -- 'Уровень 1', 'Уровень 2', ...
  description text                 -- краткое описание ("самый высокий уровень" и т.д.)
);

master_skills (
  id bigserial primary key,
  code text not null,              -- внутренний код навыка
  name text not null,              -- название ("Сложные работы с мойками", ... )
  description text,                -- описание навыка
  is_complex boolean default true  -- флаг "сложный навык"
  -- опционально: level_min smallint references master_levels(id) — минимальный уровень
);
```

**Что должно быть на выходе по Задаче 3.1:**

* В SQL-файле схемы (например, `01_tables.sql` или в отдельной миграции для блока 3):

  * добавлены определения таблиц `master_levels` и `master_skills` (если их не было);
  * таблицы создаются **после** основных таблиц (orders/order_execution и т.п.), чтобы порядок был логичным.
* В `master_levels` сразу вставлены 4 записи:

  * id=1 — самый высокий уровень;
  * id=2;
  * id=3;
  * id=4 — минимальный уровень.
* Все команды CREATE/INSERT проходят без ошибок при запуске в Supabase SQL Editor.

**Критерий успешности Задачи 3.1:**

* SQL-скрипт выполняется без ошибок.
* В Supabase видно таблицы `master_levels`, `master_skills`.
* В `master_levels` есть ровно 4 записи.
* Не изменены/не сломаны существующие таблицы.

   * Добавить вспомогательную функцию, например:
     `getMasterTimeFactor(masterLevelId)`, которая:

     * пока возвращает **1.0** для всех уровней;
     * но структура функции позволяет в будущем задать разные коэффициенты.

2. Интеграция:

   * Найти место, где считается теоретическое время изготовления (если уже есть).
   * Аккуратно встроить вызов `getMasterTimeFactor(masterLevelId)`, **но так, чтобы текущие значения времени не изменились** (если нужно — временно выводить результат в отдельное поле, либо просто логировать в консоль).
   * Убедиться, что в объекте расчёта хранится:

     * `masterLevelId`
     * `masterSkills` (массив id навыков)

3. Ничего не ломаем:

   * Любые изменения в расчётной логике делаем так, чтобы текущий результат для уже сохранённых заказов **не поменялся**.
   * Если есть риск изменить числа — лучше ограничиться подготовительными комментариями и вспомогательной функцией, без применения коэффициента.

**Критерий успешности Задачи 3.4:**

* В коде есть явная точка расширения: `getMasterTimeFactor(masterLevelId)` или аналогичная функция.
